# 0003. 本期不建退款表，以 `refund_required` 狀態留出口

- 狀態：已採納
- 日期：2026-10-22
- 相關：`docs/erd.md`「已排除」、`docs/state-machines.md` §2、§3「一筆訂單可以跨場次嗎？」

## 背景

真實票務系統需要退款：使用者退票、活動取消、遲到的付款（訂單已逾期但金流仍收到錢）。
完整的退款流程牽涉：

- 部分退款（一筆訂單 3 張只退 1 張）
- 手續費由誰負擔
- 各家金流退款 API 的差異與非同步結果
- 一筆付款被多次部分退款的對帳

本專案的主線是**高併發防超賣**與**金流回調冪等**。退款能展現金流對帳的深度，但流程長，對主線沒有貢獻。

另一方面，活動或場次被取消時，已付款的訂單**一定要有地方可去**，不能停在 `paid` 假裝沒事。

## 決定

1. 本期不建 `refunds` 表，不串接金流退款 API
2. `orders.status` 保留 `refund_required`（待人工退款，終態）作為出口
3. 只有一條箭頭會進入這個狀態：`paid → refund_required`（活動或場次取消，由主辦方觸發）
4. 使用者自行退票不在本期範圍，狀態機上不畫這條箭頭
5. 一筆訂單只能購買同一場次的票種（應用層驗證，W9 實作），避免「取消一場、退一部分」的部分退款情境

退款本身由人工在金流後台處理，系統只負責把需要退款的訂單標記出來。

## 考慮過的選項

| 選項                                       | 優點                             | 缺點                                                 |
| ------------------------------------------ | -------------------------------- | ---------------------------------------------------- |
| **A. 只留 `refund_required` 狀態（採用）** | 範圍小；取消活動時訂單有明確去處 | 退款執行與結果不在系統內                             |
| B. 完整 `refunds` 表 + 金流退款 API        | 功能完整，可展示對帳             | 部分退款、手續費、各金流差異會佔掉大量時程，偏離主線 |
| C. 完全不處理，取消活動時訂單維持 `paid`   | 最省事                           | 已付款訂單無處可去；報表會把要退的錢算成營收         |

選項 C 違反這個專案的原則：**範圍外的東西要留出口，不要留空白。**

## 後果

**好處**

- 範圍控制住，時程留給防超賣與金流冪等
- 活動取消時，「哪些訂單要退錢」可以直接用 `status = 'refund_required'` 查出來
- 「一筆訂單只含一個場次」讓取消、退款、驗票三條路徑都不必處理跨場次分支

**代價**

- 退款要人工處理，退了沒、退多少，系統內沒有紀錄
- 使用者無法自行退票
- 想買兩個場次的使用者要下兩筆訂單、付兩次款

**擴充點**

- 新增 `refunds` 表關聯 `payments`（一筆付款可對應多筆部分退款），記錄金額、手續費、金流退款序號與狀態
- 使用者退票：在訂單狀態機補一條 `paid → refund_required`〔使用者觸發〕
- 放寬單場次限制：`order_items → ticket_types → event_sessions` 已能取得場次，不需改表結構
