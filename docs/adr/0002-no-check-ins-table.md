# 0002. 核銷不另建表，記在票券上

- 狀態：已採納
- 日期：2026-10-22
- 相關：`docs/erd.md`「已排除」、`docs/state-machines.md` §1、§4.2、`docs/events.md` §4

## 背景

現場驗票有兩種需求：

1. **正確性**：一張票只能成功入場一次。兩個驗票員同時掃同一張票，只能有一個成功。
2. **歷史**：每一次掃碼都要留紀錄，包含失敗的（查無此票、場次不符、已作廢、重複掃碼……），供現場顯示「已於 19:02 由 A 閘口入場」，以及事後稽核。

常見做法是建一張 `check_ins` 核銷表，每次成功入場新增一筆，並用 UNIQUE 約束擋重複。

## 決定

不建 `check_ins` 表。兩種需求分別由兩個地方負責：

| 需求   | 負責的地方                                                  | 機制           |
| ------ | ----------------------------------------------------------- | -------------- |
| 正確性 | `tickets.checked_in_at`、`checked_in_by`、`checked_in_gate` | 條件更新       |
| 歷史   | `scan_logs`（每次掃碼一筆，含失敗）                         | 只新增、不修改 |

核銷就是一條條件更新：

```sql
UPDATE tickets
SET checked_in_at = NOW(), checked_in_by = ?, checked_in_gate = ?
WHERE id = ? AND checked_in_at IS NULL AND voided_at IS NULL
```

影響 1 筆就是入場成功，0 筆就是已被使用或已作廢。並發的兩個請求由資料庫的列鎖保證只有一個拿到 1，不需要額外的 UNIQUE 約束：一張票只有一列，也就只有一個 `checked_in_at`。

## 考慮過的選項

| 選項                                                        | 優點                                                  | 缺點                                                                          |
| ----------------------------------------------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------------- |
| **A. 時間欄位在 `tickets` + `scan_logs`（採用）**           | 「是否已入場」只有一個來源；驗票是單列更新，不用 join | 不支援再入場                                                                  |
| B. `check_ins` 表 + `ticket_id` UNIQUE                      | 核銷紀錄獨立                                          | 「是否已入場」有兩個來源；仍需要 `scan_logs` 記失敗，變成三個地方描述同一件事 |
| C. 只有 `scan_logs`，用 `result = 'success'` 判斷是否已入場 | 表最少                                                | 判斷入場要查紀錄表；並發時兩筆都可能寫入 success，正確性要另外加鎖            |

選項 B 的問題是**同一個事實有兩個來源**：`tickets` 上若有任何狀態，就會和 `check_ins` 有沒有那一筆產生「誰說了算」的問題，遲早對不起來。
選項 C 把正確性交給一張只新增的紀錄表，等於放棄資料庫的條件更新這個最便宜的並發保證。

原則：**狀態欄位要跟條件更新的 `WHERE` 打在同一組欄位上**；歷史紀錄另外存，只新增、不改寫。

## 後果

**好處**

- 「這張票入場了沒」只看 `tickets` 一列，驗票 API 和統計都直接
- 並發正確性由單一條件更新保證，容易寫測試證明
- `scan_logs` 只新增，失敗與重複掃碼都留得下來

**代價**

- 不支援中場離場再入場：一張票只有一個 `checked_in_at`
- 「核銷時間」在 `tickets` 和 `scan_logs` 的成功紀錄裡各有一份。以 `tickets` 為準，`scan_logs` 只當歷史，兩者寫在同一個交易裡

**擴充點**

- 要支援再入場時，可在 `tickets` 加 `inside` 之類的狀態，搭配 `scan_logs` 記錄進出；或屆時再寫新的 ADR 改用獨立的進出紀錄表
- 離線驗票上傳的紀錄同樣寫進 `scan_logs`（已預留 `device_id`），衝突以 `tickets` 的條件更新結果為準
