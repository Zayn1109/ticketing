# 0005. 租戶由網址路徑決定，查詢明確從主辦方往下

- 狀態：已採納
- 日期：2026-10-27
- 相關：[ADR 0004](0004-organizer-roles-are-permission-levels.md)、`docs/permissions.md`

## 背景

多個主辦方共用同一套系統與資料庫，必須保證彼此看不到、也改不到對方的資料。
一個使用者可以同時屬於多個主辦方，且在各主辦方的角色不同（例如在甲是 admin、在乙是 scanner）。

要決定三件事：

1. 系統如何得知使用者「現在在操作哪個主辦方」
2. 查詢時如何確保只取到該主辦方的資料
3. 存取被拒時回應什麼

## 決定

### 1. 租戶放在網址路徑

主辦方後台的路由一律以主辦方開頭：

```
/organizers/{organizer}/events
/organizers/{organizer}/events/{event}/edit
```

### 2. 查詢明確從主辦方往下，不使用 Global Scope

```php
$organizer->events()->findOrFail($id);   // ✅
Event::findOrFail($id);                  // ❌ 在後台路由中不這樣寫
```

每個請求經過三層檢查：

| 層  | 機制                                  | 問的問題                         | 失敗時 |
| --- | ------------------------------------- | -------------------------------- | ------ |
| ①   | Middleware                            | 使用者是這個主辦方的成員嗎？     | 404    |
| ②   | Scoped Binding（`->scopeBindings()`） | 網址中的子資源屬於這個主辦方嗎？ | 404    |
| ③   | Policy                                | 使用者的角色可以做這個動作嗎？   | 403    |

### 3. 非成員回 404，成員權限不足回 403

- 非成員：回 404，不透露主辦方是否存在
- 成員但角色不足：回 403，對方本來就知道主辦方存在

## 考慮過的選項

**租戶從哪裡來**

| 選項                           | 優點                                               | 缺點                                                               |
| ------------------------------ | -------------------------------------------------- | ------------------------------------------------------------------ |
| **A1. 網址路徑（採用）**       | 網址即上下文；多分頁各自獨立；可加入書籤、分享連結 | 網址較長                                                           |
| A2. Session 中的「目前主辦方」 | 網址乾淨                                           | 多分頁時，在分頁 2 切換主辦方後，分頁 1 送出的表單會寫入錯誤的租戶 |
| A3. 子網域                     | 品牌感                                             | 本機與部署都要處理 DNS、Cookie 網域，與本專案主線無關              |

A2 的失敗模式正是隔離要防止的事（資料寫入錯誤租戶），而且在後台操作中很容易發生。

**查詢如何過濾**

| 選項                                             | 優點                               | 缺點                                                                                                                                         |
| ------------------------------------------------ | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **B1. 明確從主辦方往下查（採用）**               | 過濾條件寫在程式碼上，閱讀時看得到 | 要靠紀律與測試確保沒有漏寫                                                                                                                   |
| B2. Global Scope 自動加 `WHERE organizer_id = ?` | 不會忘記                           | 規則隱藏；排程與佇列沒有「目前主辦方」，容易誤用或需要逐處解除；`event_sessions`、`ticket_types` 沒有 `organizer_id`，需額外 join 或去正規化 |

B1 漏寫的風險，由階段 6 的隔離測試補上：每個後台路由都要有「其他主辦方的成員存取 → 404」的測試。

## 後果

**好處**

- 租戶上下文明確，不依賴伺服器端狀態
- 三層檢查各自單純，可分別測試
- 子資源跨租戶存取由框架的 Scoped Binding 擋下，不必每個 controller 手寫檢查

**代價**

- 每個後台路由都要帶 `{organizer}` 參數
- 沒有自動防護，新增路由或查詢時忘記從主辦方往下查，只能靠測試發現

**擴充點**

- 若之後需要「預設主辦方」體驗，可在登入後導向使用者上次使用的主辦方網址，仍以網址為唯一上下文
- 需要時可再加 Global Scope 作為第二道防線，但不取代明確查詢
