# 0004. 主辦方角色是權限等級，採固定三級

- 狀態：已採納
- 日期：2026-10-27
- 相關：`docs/permissions.md`、`docs/erd.md`（`ORGANIZER_USER`）

## 背景

一個使用者可以屬於多個主辦方，在每個主辦方各有一個角色，記在 `organizer_user.role`，合法值為 `owner` / `admin` / `scanner`。

討論時出現一個疑問：「scanner 聽起來像職稱，但驗票只是員工會做的其中一件事，admin 也應該能驗票。」
這暴露出角色欄位的定位需要先講清楚：它描述的是**職務**，還是**權限**？

另外要決定權限模型的粒度：固定幾個角色，還是做成可自由組合的權限表。

## 決定

1. **`role` 是權限等級，不是職務。** 系統不記錄職務；行銷、客服、現場人員都可能是 `admin`。
2. **固定三級，由上往下包含**：`owner ⊇ admin ⊇ scanner`。admin 能做 scanner 能做的所有事，因此 admin 也能驗票。
3. **`scanner` 代表「只能驗票」的最小權限等級**，用於活動當天臨時加入的工讀生、志工。名稱維持 `scanner`，以本 ADR 與 `permissions.md` 的定義為準。
4. 各級能做的事見 `permissions.md`，其中幾個邊界決定：
   - admin 只能邀請、移除 scanner；任免 admin 與 owner 只有 owner 能做
   - 取消活動或場次只有 owner 能做
   - 一個主辦方可有多個 owner，但最後一個 owner 不能被移除或降級
   - scanner 只能看到當下掃到的票的持票人資料，不能瀏覽名單
   - scanner 本期可驗該主辦方所有場次

## 考慮過的選項

**粒度**

| 選項 | 優點 | 缺點 |
|---|---|---|
| **A. 固定三級（採用）** | 判斷只需比較角色；容易測試；涵蓋本專案需求 | 無法為個別成員客製權限 |
| B. 權限表（角色 ↔ 權限多對多，如 spatie/laravel-permission） | 彈性最大 | 多兩到三張表與一個套件；權限組合爆炸，測試面變大；本期沒有需要客製的情境 |
| C. 只有 owner / member 兩級 | 最簡單 | 臨時驗票人員只能給 member，等於讓工讀生看到銷售報表與購票名單 |

C 違反最小權限原則；B 的彈性目前用不到。A 是能滿足「臨時人員只能驗票」的最小設計。

**是否保留「只能驗票」這一級**

把驗票當成所有成員的共同權限、只留 owner / admin 兩級，看似更符合「驗票不是職稱」的直覺，但會失去最小權限：KKTIX 的驗票帳號、Eventbrite 的 check-in staff 都是同樣的設計，理由相同。

**`scanner` 是否改名**（例如 `checkin_staff`）

改名能讓名稱更直接表達權限範圍，但需要 `migrate:fresh` 並同步兩台開發機。名稱的歧義由本 ADR 的定義消除，暫不改名。

## 後果

**好處**
- 權限判斷集中在「使用者在此主辦方的角色」一個來源，對應 `User::roleIn()`
- 三級包含關係讓判斷可寫成「至少是某一級」，不必逐一列舉
- 高風險操作（取消、任免管理者）集中在 owner

**代價**
- 無法做「這位 admin 不能看報表」之類的個別調整
- `scanner` 的名稱仍可能被誤讀為職稱，需靠文件說明

**擴充點**
- 指定場次的驗票權限：新增成員與場次的關聯表
- 需要細粒度權限時改用權限表，另寫新的 ADR 取代本篇
