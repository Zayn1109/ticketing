# 0001. 場地資訊不獨立成表

- 狀態：已採納
- 日期：2026-10-22
- 相關：`docs/erd.md`「已排除」、`docs/events.md` §1「場次已新增」

## 背景

每個場次都需要場地資訊：場地名稱、地址，以及決定開演時間怎麼顯示的時區。
Event Storming 時留下的問題是：「同一場地會重複使用嗎？要不要獨立成實體？」

票務平台的上游是主辦方。主辦方在乎的是「這場活動在哪裡辦」，不需要維護一份場館資料。

## 決定

不建 `venues` 表。場地資訊以欄位形式放在 `event_sessions`：

| 欄位            | 說明                              |
| --------------- | --------------------------------- |
| `venue_name`    | 場地名稱，自由文字，必填          |
| `venue_address` | 地址，選填                        |
| `timezone`      | IANA 時區名稱，預設 `Asia/Taipei` |

## 考慮過的選項

| 選項                                     | 優點                                                     | 缺點                                                                                                                     |
| ---------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **A. 欄位放在 `event_sessions`（採用）** | 建場次一步完成；少一層關聯；場次就是場地資訊的唯一使用者 | 名稱無法正規化                                                                                                           |
| B. 獨立 `venues` 表                      | 同場館可重用；可依場館搜尋、統計                         | 要先建場館才能建場次；誰能新增、修改場館（平台？各主辦方？）變成新的權限問題；改了場館資料會連帶改到已結束活動的歷史顯示 |

選擇 A 的關鍵理由是**領域邊界**：我們是售票方，主體是活動，不是場館經營者。
B 的好處（搜尋、統計、重用）都不在本專案的主線（防超賣、金流冪等）上，卻會帶進一整組新的權限與資料維護問題。

另外，場地資訊屬於「當時的事實」。某場次在哪裡辦，辦完就不該再變；放在場次上剛好就是一份快照，不會因為之後改了場館資料而影響歷史紀錄。

## 後果

**好處**

- 主辦方建立活動的流程較短，不必先管理場館
- 場次自帶場地快照，歷史資料穩定

**代價**

- 場地名稱是自由文字，同一場館可能寫成「台北小巨蛋」、「臺北小巨蛋」、「小巨蛋」，依場館搜尋與統計會不精準
- 無法做「這個場館接下來有哪些活動」這類功能

**擴充點**

- 將來需要時，新增 `venues` 表並在 `event_sessions` 加上可為 NULL 的 `venue_id`。既有的 `venue_name`、`venue_address` 保留作為快照，不必搬資料
- 時區已經在場次上，抽出場館時不影響時間的計算與顯示
